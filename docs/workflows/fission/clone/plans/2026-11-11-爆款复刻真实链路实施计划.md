## 3. 节点、工作副本与提交边界

四节点 ID 和产物引用由 Contracts 集中定义。作用域为当前项目、`workflow=FISSION`、`space=FISSION_CLONE` 和实际 `workflowRunId`。当前已交付范围见本计划开头，后文保留局部重做、批内删除等目标的提交规则。

| 节点 / nodeId                 | 直接上游与编辑草稿                                                              | 工作副本及提交边界                                                                                                                 | 下游                    |
| ----------------------------- | ------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ----------------------- |
| 上传素材 / `CLONE_INPUT`      | 项目、参考视频及商品文件/资产精确版本；草稿保存上传引用、商品说明、来源使用确认 | `clone-input`：用户明确确认输入才提交；普通草稿保存不提交，上传成功本身只落工作区文件                                              | 拆解                    |
| 深度拆解 / `CLONE_ANALYSIS`   | 已提交 `clone-input` 的 artifactId/revision/hash；人工编辑报告独立于确认版      | `clone-analysis`：完整拆解成功且服务端校验后自动提交；人工编辑明确保存才提交，取消不变更确认版                                     | 映射                    |
| 元素映射 / `CLONE_MAPPING`    | `clone-analysis`、商品事实与当前项目资产精确版本；编辑保留/替换配置             | `clone-mapping`：全部必换产品和 replace 项有效、结构锁定配置一致时人工确认提交                                                     | 成片生成                |
| 成片生成 / `CLONE_GENERATION` | 已确认 input/analysis/mapping 和生成设置；数量、批次选择属于节点草稿            | `clone-batch:<batchId>` 与 `clone-video:<variantId>`：整批请求数量全部完成、文件与质量校验通过后原子提交；不增加人工“完成校验”步骤 | 下载、明确归档/完成交付 |

- `WorkflowNodeState.revision` 是编辑冲突版本；`WorkingArtifact.revision` 是确认内容版本；任务 attempt、批次序号和列表名称均不替代业务 revision。
- 指纹只包含规范化业务内容、稳定文件身份/哈希与明确版本引用，不包含进度、时间戳、预览地址或签名 URL。同内容确认、重复完成回调不增 revision。
- 下游保存真正消费的 `artifactId + revision + contentHash`。普通输入编辑不使确认产物失效；上游确认内容改变后，递归标记已存在且实际依赖它的下游待更新，不创建空副本。
- 草稿、部分失败结果、待修正结果不冒充正式工作副本。已有完整批次在后续任务失败时保持可读；源变化可以标记待更新，不删除旧交付、不自动付费重生成。
- 普通节点导航只 activate，不确认、不创建任务。明确“确认并下一步”可以先确认再导航。拆解自动成功后不要求重复人工确认。
- 本期不新增复刻版本树和自动分叉。显式新批次创建新的 batch/variant ID；对已有条目的局部重生成沿用 variant ID，成功原位提交，失败保留旧内容。两者不可混用。
- 整批提交后纯删除只更新当前批次成员及对应工作副本可用性，不调用模型、不触发重渲染。请求数量及原始任务审计保持不变；删除动作不会使批次被自动补足。已归档项目资产遵循资产自己的生命周期。

首次批次与后续局部更新使用不同的提交范围：

- 首次批次必须 N 条全部可交付，才原子提交 N 个 video 副本及 batch 清单；批次清单依赖每条实际 video 的 artifactId/revision，video 自己记录消费的上游引用。
- 已提交批次的局部重生成只原子提交目标 video 和更新后的 batch 清单；批次可以包含来自不同确认来源的条目，逐条保留来源快照，不把批次头写成所有条目共同消费的新版本。未更新兄弟继续待更新，批次返回 stale 条目数，不能因一项更新将整批标为 CURRENT。
- 局部更新失败/取消不改变旧 video/batch；纯删除在一个事务内移除清单成员及其依赖，标记被移除工作副本不可用，不影响未删兄弟。成员实际变化才增加 batch revision，重复删除为幂等无变化。
- 在首次整批提交前若需按新来源重生成，只能显式取消旧批次后建立新批次；不能把不同来源的部分结果拼成一次首次整批成功。
- 首次提交前不能通过删除失败条目降低 requestedCount 来取得成功；停止剩余生成应取消批次，已有成功检查点留在任务结果区，不自动发布为较小批次。

## 4. 共享契约设计

G1 已导出 `packages/contracts/src/fission-clone.ts` 输入契约；G2 已导出 `fission-clone-analysis.ts` 报告、映射、任务及内部快照契约，并发布 JSON Schema 和 fixture 供 Python 消费。`fission-clone-generation.ts` 及生成 schema 仍拟新增。以下保留完整跨阶段设计，具体已实现能力以业务指南和共享类型为准。

### 4.1 公共字段与输入

- `schemaVersion`；projectId、workflowRunId、artifactId、assetId、fileObjectId、taskId、batchId、variantId、shotId、elementId 明确区分。
- `ArtifactRef={artifactId,revision,contentHash}`；`AssetVersionRef={assetId,version}` 必须服务端解析为当前项目的稳定内容；文件引用至少携带 fileObjectId、sha256、sizeBytes、媒体元数据。跨项目导入另留 sourceProjectId/sourceAssetId/sourceVersion。
- 时间线统一整数毫秒 `startMs/endMs/durationMs`，帧率明确有理数或可精确换算表示；ISO 时间带时区，比例字段注明 0–1。不以 `00:03–00:07` 展示字符串作计算或定位依据。
- 分析时间保留毫秒；生成时冻结输出恒定帧率 `fpsNumerator/fpsDenominator`，将绝对边界统一换算为帧索引：`floor(timeMs × fpsNumerator / (1000 × fpsDenominator) + 0.5)`，区间采用左闭右开。相邻镜头共用同一个边界，不能分别舍入时长后累加；映射到零帧的镜头在渲染前阻断。编译后的帧时间线随 VariantPlan 保存，合成与验收使用同一份结果。
- 转场在既定输出时间线上占用明确的重叠帧区间，冻结其起止和两侧素材截取范围，不因加入转场缩短总片长或移动后续边界。素材不足以支撑转场时明确阻断；G0 的本地媒体样本须覆盖转场、分数帧率和短镜头，验证总帧数及边界不累积漂移。
- `CloneInput`：一条参考视频、商品名称/已提供事实与依据、多角度商品素材、有权使用来源的确认。商品事实约束只来自当前输入，不能继承原商品功效。文件探测结果与用户描述分开。
- 上传限制集中定义并由能力接口返回，服务端同时校验文件签名、类型、大小、时长、可解码性和资源上限。G1 参考 MP4/MOV 上限 256 MiB（受更严格 `MAX_UPLOAD_BYTES` 限制），商品文件 JPG/JPEG/PNG/WebP/MP4/MOV 每份 64 MiB、最多 20 份，视频 1–120 秒，像素数不超过 4096×2160。这是输入接收上限，不代表生成模型支持范围。原 500MB/200MB、1–100 条为演示值；后续正式生成能力须经 G0/G3 验证，目标仍为单批不少于 20 条。

### 4.2 六维报告与时间线

下表描述完整业务目标。G2 当前只分析采样画面，音频字段保留结构但语义为 `UNASSESSED`，不执行转录、节拍/音效检测；人工保存同样受限。缺乏分析能力时不能用“未检测到”冒充分析结论。

| 维度 | 必须表达的业务内容                                                           |
| ---- | ---------------------------------------------------------------------------- |
| 结构 | 稳定 stageId、阶段时间/占比、叙事作用、钩子/转化点区间、节奏曲线             |
| 创意 | 核心概念、情绪共鸣、反差、记忆点；关联证据区间                               |
| 产品 | 原产品元素、出镜区间、角度、特写占比、效果表达及能否迁移                     |
| 镜头 | 稳定 shotId、起止、景别、运镜、转场、构图、可见元素及证据帧                  |
| 音频 | 有无口播、语速/音色观察、BGM 风格/节拍、音效卡点、静音区间；转录内容与置信度 |
| 视觉 | 字幕内容/样式、滤镜色调、贴纸、画幅和安全区；烧录元素与独立轨道区分          |

报告同时含 `elements[]`（稳定 elementId、类型、出现的 shotId/区间）、迁移建议、来源依据、置信度、无法识别/不适用原因。可见画面、转录事实与模型推断分开；未检测到 BGM/口播等返回未检测到或不适用，不编造 112 BPM、固定六镜头、固定 32 秒等演示值。

服务端验证六维完整、ID 唯一、镜头/阶段有序且边界合法、覆盖与占比一致、引用存在；允许真实缺项有明确原因。整份报告及关联文件完整才自动提交。人工调整镜头范围后重新验证所有引用；不自动用旧映射套新镜头。

### 4.3 映射、结构锁定与生成输出

- `CloneMapping.bindings[]`：elementId、类型（product/person/scene/subtitle/bgm/voiceover）、`KEEP|REPLACE`、目标资产版本或明确文本/样式/音色配置、适用 shotId。所有产品必换项逐项校验；不以“至少一个产品已映射”代替全部完成。
- 保留/替换以元素实例为单位；目标类型、可访问性、文件可用性及版本由服务端校验。保留人物/场景指保留其配置与视觉特征目标，不承诺生成像素完全一致。
- 商品事实、用户确认的 KEEP/替换目标及 StructureLock 均为硬约束，彼此冲突时阻断确认并指出冲突项；差异化策略只在这些约束共同允许的范围内执行。映射显式记录锁定属性与允许变化维度，绑定的精确人物/场景资产不得为凑数量而自动更换。请求数量在允许变化范围内无法形成足够创意时，提示用户调整策略或数量，不自动解锁或缩减本批目标。
- `StructureLock` 冻结镜头顺序、stageId、时间边界/占比、节拍/音效锚点、钩子和转化位置。用户确认的锁定内容进入映射及每批输入快照。
- BGM/口播 KEEP、字幕/贴纸 KEEP 必须有真实可执行方案：可用授权轨道，或已验证分离/提取/重建方案。无独立音轨、烧录内容无法可靠移除时阻断对应模式并给出替换方案，不能显示“保留成功”。文字替换为目标商品时同步避免残留原商品名称。
- 口播/字幕分别表达内容策略与表现形式策略：保留原音频/原文本，或替换文本并保留已支持的音色、语速、字幕样式；不能以一个 KEEP 同时隐含两种含义。确认映射前，保留文本须经 AI 基于目标商品事实核对并保存依据，不能靠关键词完成语义判断。包含原商品名称或无依据功效时阻断原内容保留，用户改为文本替换后重新合成/对齐；无法可靠转录时不开放原内容保留。保留音色仍受能力接口约束，不承诺任意声音克隆。
- 文本核对使用本计划拟新增 mapping 异步任务的 `VALIDATE_KEEP_TEXT` 执行目的，智能匹配使用 `SMART_MATCH`，两者仍属于 MAP_SUGGEST 操作且由用户显式触发。手工映射可独立发起文本核对，无须先运行智能匹配；任务冻结商品事实来源、保留文本、内容策略及映射草稿 revision/hash。确认接口只校验核对证据与当前实际消费内容一致，缺失或过期则返回待核对原因，不同步调用模型或隐式创建付费任务。证据按来源与内容哈希绑定，草稿 revision 用于防并发覆盖；纯导航不使语义证据失效。
- `CloneGenerationRequest`：idempotencyKey、expectedDraftRevision、expected 上游引用及目标 revision、requestedCount、画幅/分辨率/渲染能力选择、差异维度策略。种子、内部模型 ID 和 Prompt 编译快照仅在内部协议，不向普通详情暴露。
- `VariantPlan`：固定 variantId、各镜头创意/映射/素材引用、事实依据、音画时间线、Prompt 及版本、差异化说明；`VariantResult`：任务阶段、文件引用/哈希、真实媒体元数据、缩略图、质量报告、可交付状态。文件 URL 为读取时权限投影。
- 内部执行协议补 `planHash`、`repairAttemptId`、步骤依赖和质量缺陷定位；返修尝试与任务 attempt 均不是业务 revision。恢复请求区分执行重试、原快照质量返修和最新来源重生成，并携带幂等键及目标版本。质量报告列出缺陷 ID、shotId/轨道、证据、阻断原因与可执行恢复动作；WARNING/FAILED 不计入可交付数量，具体处理见第 6.3 节。
- `VariantPlan` 完整内容属于内部执行协议；公开 DTO 只投影差异化说明、来源摘要、可见阶段和质量依据，不直接透传内部 Prompt。
- 状态必须区分任务执行（QUEUED/RUNNING/SUCCEEDED/FAILED/CANCELLED）、条目状态及质量（PENDING/PASSED/WARNING/FAILED/NOT_EVALUATED）、批次聚合 PARTIAL；不把质量告警、部分成功合并成成功。实现前对齐既有状态语义，集中导出复刻状态，不能假定仓库已有通用 Task 枚举。
- 新增复刻领域错误到共享 `ApiErrorCode`，覆盖来源变更、草稿冲突、错误作用域、资产不可用、配置缺失、能力不支持、未知创建结果、质量阻断；复用既有适用错误码，响应继续使用 `ApiResponse<T>`，列表分页遵循现有模式。

`analysis/draft` 与通用节点草稿必须写同一份编辑状态、同一 expectedRevision，领域入口只补报告校验，不创建第二份草稿。确认和任务创建均须与该编辑版本对齐。

MAP_SUGGEST 创建时冻结执行目的、目标映射草稿 revision 和来源引用；SMART_MATCH 完成时在同一事务内核对来源与任务租约，并按冻结 revision 比较后写入草稿（CAS）。用户已修改草稿时，成功建议仅保留在任务结果中并标记待采用，不能覆盖或自动合并人工字段。再次采用按当前 expectedRevision 校验，来源已过期则拒绝采用；未保存的本地编辑在前端保持隔离并参与采用前的冲突处理。VALIDATE_KEEP_TEXT 只保存不可变核对证据，不写映射草稿；商品事实或保留内容变化后旧证据不能用于确认。通用节点草稿乐观锁可复用，不另建第二套可写映射草稿。

部分成功文件可在任务结果区受控预览，但不能冒充正式工作副本、整批导出或归档。正式 export 只接收已提交且可用的条目；源已更新但旧交付仍存在时，明确标为旧快照，不静默按最新来源重渲染。导出冻结选中条目的 artifactId/revision/fileHash；ZIP 打包若较耗时使用 EXPORT 持久化任务，经生成 Worker 的无模型执行分支处理，不调用渲染 Provider。

归档资产稳定幂等键按 Run+variantId 定义，操作收据键再包含 artifactId+revision；同版本重复点击不新增版本，显式归档新 revision 才更新同一资产的版本。多条归档逐条记录收据与失败项，重试只补未完成项，不将部分入库显示为全部成功。

### 5.2 持久化与事务

G1 已新增 `FissionCloneUpload`：项目/Run 复合隔离、scoped clientUploadKey 唯一约束、独立 attemptToken、角色、上传状态、FileObject 引用、媒体数据、精确来源资产版本和过期时间。可用上传关联为草稿文件保活；重试旋转 attemptToken，暂停恢复废弃未完成尝试。表不存 storageKey，存储身份沿用 FileObject。

复刻使用 `FissionCloneTask`、`FissionCloneTaskStep`、`FissionCloneFileHold` 和 `FissionCloneMappingFile`。G3 使用同表协调记录与条目，在 Run 锁内完成同步规划和组内发布。任务与结果记录执行事实，确认内容通过 WorkingArtifact 管理。以下保留目标设计，独立异步规划、EXPORT 和大型批次聚合仍待后续实施。

- Task：projectId、workflowRunId、operation、batch/item 作用域、idempotencyKey、inputHash、不可变 inputSnapshot、status/progress、attemptCount/attemptToken/leaseExpiresAt、取消标记、安全错误与时间。JSON 只存结构化快照，不存文件正文或签名地址。
- GENERATE 区分批次协调任务与条目子任务，使用同一任务表的 parentTaskId 和明确作用域建立关系。协调任务持有公共规划/最终提交步骤，条目子任务持有编译、渲染、合成和质检步骤；两者分别校验租约。公共规划确认后才派发条目执行，只有协调任务可做首次整批提交；子任务完成仅表示可供聚合的执行结果，不提前发布 video 工作副本。创建条目、派发与聚合恢复都须幂等，不能由任意条目重试隐式重跑全批规划。
- Step：任务/条目/镜头/阶段/返修尝试唯一键、inputHash、outputHash、状态、供应商请求/任务 ID、恢复所需输出引用。旧 attempt 不得继续写入；新 attempt 可验证来源快照、计划/步骤输入哈希、输出哈希及文件身份后，继承已持久化且未被返修失效的检查点和 providerTaskId。步骤哈希包含其实际消费的计划、Prompt、参数和上游步骤输出；不同输入/Run 的检查点不得采用。
- Batch/Item：requestedCount、固定 variantId、当前条目采用文件、聚合状态、来源引用与生成设置；分页排序使用稳定字段。重试不重建成功条目，重生成不换 variant ID。
- 对 project/run、task/item/step/fileHold 建复合隔离外键和索引；幂等键在 project/run/operation/业务对象内唯一。相同幂等键不同输入返回冲突；活动互斥用数据库约束或事务锁保证，不能只禁用按钮。
- 同 Run 的上游确认/报告编辑提交与依赖它的活动 ANALYZE/MAP_SUGGEST/GENERATE 任务采用互斥门禁：任务期间可浏览和保存隔离草稿，不能悄悄替换确认来源。EXPORT 消费冻结交付文件，不锁上游编辑或条目重生成。提交仍按操作类型校验，防管理员操作、恢复或迟到请求绕过门禁。
- 用户草稿/确认写入校验当前编辑 Run 及编辑代次；Worker 按冻结 task 所属 Run 校验，不依赖前端当前选中的 Run。仅因退出而 PAUSED 的 Run 允许后台完成；取消、删除或终结门禁对所有任务生效。所有完成操作重验 lease、attempt、取消状态与文件身份；业务校验按下表区分，不能统一要求所有来源仍是最新版本。按首次整批/局部更新范围与任务终态同事务提交，失败回滚，保留原提交。
- `WorkflowWorkingRepository.commitValidatedArtifactsInTransaction` 可复用提交与指纹，但当前通用 upsert 在内容变化时写入 `freshness=CURRENT`，不提供复刻批次聚合语义。领域服务须在同一事务内按保留成员计算 batch freshness/availability 及 stale 数量：任一保留成员待更新，批次仍待更新；全部成员当前且可用才恢复当前。纯删除也重算，删除最后一个待更新成员后可恢复当前；空批次单独投影为空、禁用交付，不能视作新的完整生成成功。状态重算本身不增加业务 revision，清单成员或实际内容变化按指纹增版。不得通过修改兄弟 freshness 或放松其他流程校验来实现。
- 通用 `executionInputHash()` 不能代替复刻输入/生成设置 hash，必须显式构造白名单业务快照。
- retry/repair 保持原来源快照；来源已失效且不能提交时，已提交条目提示按最新配置重生成，首次未提交批次提示取消后新建，不能自动换输入。已成功供应商步骤先查持久化 ID/结果再恢复；只有明确的质量返修可使相关成功步骤失效并产生新调用。
- 状态转换集中校验：QUEUED→RUNNING→SUCCEEDED/FAILED/CANCELLED；失败只有显式重试才回 QUEUED，取消不直接变成功。租约过期由持久化恢复扫描以事务和 Outbox 重新投递，限制重领次数，不能依赖浏览器轮询启动恢复；成功终态重复 complete 返回原收据。

| 操作        | 完成校验与提交范围                                                                                                                                                                                                                                                                 |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ANALYZE     | 确认 input 的 artifactId/revision/hash/freshness、目标报告 expectedRevision、报告完整性；自动提交确认报告，保留并标识用户并发编辑的草稿，不覆盖其未采用编辑                                                                                                                        |
| MAP_SUGGEST | 确认来源当前性；SMART_MATCH 按第 5.1 节草稿 CAS，冲突保留待采用建议；VALIDATE_KEEP_TEXT 保存绑定来源与内容哈希的证据。两种目的均不推进映射工作副本 revision                                                                                                                        |
| GENERATE    | 冻结来源当前性、目标 expectedRevision、准确数量及质量；子任务检查点不发布产物，协调完成按首次整批或局部更新范围提交                                                                                                                                                                |
| EXPORT      | 创建时原子校验选中条目已提交且可用，冻结 artifactId/revision/fileHash、文件引用并建立 hold；完成时校验冻结清单、文件身份、hold、访问权限及取消状态，不要求 artifact 仍指向该 revision 或来源 CURRENT。后续原位重生成不改变本次导出；结果明确标注导出快照，文件丢失或权限失效则失败 |

### 5.3 文件生命周期、迁移与上线

- 先通过 StoragePort 落文件并探测，再以事务绑定 FileObject、任务检查点或副本；事务失败将无主文件列入清理。数据库事务不包含外部生成、存储调用和 FFmpeg。
- 冻结输入和保留/替换素材建立真实 file hold/关联，覆盖排队、运行、失败可恢复、部分完成及成功提交后的引用。上游换文件不得清掉活动任务或仍有效结果使用的旧文件。

## 6. Worker 与 AI/媒体执行

拟新增两个独立运行单元：`workers/fission-clone-analysis`（拆解、映射建议）与 `workers/fission-clone-generation`（创意、Prompt、渲染、合成、质量、交付打包）。业务包互不导入；真正重复且契约一致的传输能力使用 `workers/shared/ai-runtime`。

拟定队列 `fission.clone.analysis.requested`、`fission.clone.generation.requested`，显式配置 routingKey，禁止使用 Outbox 默认效果类队列。沿用小消息 `{schemaVersion,projectId,runId,requestId}`，其中队列 `runId` 明确映射为本次 taskId，真实 workflowRunId 由受保护 claim 响应取得；若未来扩展消息，先做消费者兼容。

新增受保护内部前缀 `/internal/workers/fission-clone-analysis/tasks/:taskId` 与 `/internal/workers/fission-clone-generation/tasks/:taskId`，提供 claim、heartbeat、progress、steps/checkpoints、source content、artifacts、complete、fail。独立 Worker token guard；claim 后所有读写及文件访问校验 project/task/attempt token/租约。complete 重放幂等。Worker 不访问数据库、TOS 密钥或任意 URL。

### 6.1 拆解与映射建议

1. Claim 后读取 API 创建任务时已冻结的 input 确认版；下载受保护参考片与必要商品资料，不在领取时重新选取最新输入。
2. FFprobe/FFmpeg 探测、抽帧、镜头候选、音轨/转录与节奏证据；限制临时空间、时长、采样量和并发。上传节点不新增预处理卡片。
3. 多模态 AI 基于原片时间证据生成六维报告，识别稳定元素与可迁移逻辑；低置信项给出区间和原因。
4. 机械验证与有界结构修复：校验 JSON Schema、时间边界、ID/引用、完整性；AI 处理语义和迁移判断，不能靠关键词认定商品功效或语义相同。
5. API 原子完成并自动提交报告。人工改报告走编辑保存，不触发重新调用模型。
6. 映射辅助任务另由用户按目的触发：SMART_MATCH 读取确认报告与当前项目候选精确版本，返回建议、依据和置信度，按第 5.1 节草稿 revision 写回或保留待采用建议；VALIDATE_KEEP_TEXT 独立核对保留文本并保存证据。产品必换及当前有效文本证据仍由确认接口逐项校验。

### 6.2 成片生成

1. **输入预检**：所有来源已确认且当前，数量合法，替换完整，音画模式和模型能力可执行，保留文本的事实核对与当前映射一致。先通过确定性能力检查发现不支持的时长/参考输入/音轨处理，再进入需授权的 AI 规划；已知不支持模式不能先调用渲染再报错。
2. **差异化规划**：按请求精确规划 N 条固定 ID 版本，只变化映射允许的场景、人物、事实侧重与叙事细节；保持已确认的精确目标、镜头顺序、阶段作用、时间比例及音频锚点。所有卖点来自当前商品事实，不把原产品功效迁移为新产品事实。渲染前由 AI 全批检查计划的实际创意差异并提供对照依据，Worker 校验 ID、数量与锁定字段；差异不足可在预算内修正规划，仍不足则阻断并提示用户调整，不用种子/标题凑数。
3. **镜头 Prompt/素材编译**：每镜头引用映射与事实依据，形成一份完整音画时间线；不使用效果类用途配额、不导入其禁止口播业务规则。音频/字幕由明确轨道策略处理，防双重人声、旧产品文字及不可执行口型。
4. **受控渲染**：经独立 Provider Adapter 调用渲染能力。短镜头、长镜头或转场超出单次能力时，使用已验证的分组生成/截取方案或明确阻断；不能静默拉伸视频、删镜头来凑时长。逐项保存 providerTaskId 与镜头输出。
5. **音画合成**：按锁定时间线截取/组装、转场、字幕/贴纸、BGM/口播/音效及音量处理，FFmpeg 编码 MP4、缩略图和实际 metadata。只保留临时供应商地址作传输，不当成交付文件。
6. **质量检查**：机械检测可解码、音视频轨、时长/画幅、黑帧/静帧异常、镜头锚点；AI 审片判断目标商品、替换自然度、主体稳定、原商品残留、叙事/结构继承及计划差异是否实际呈现。报告含具体镜头和证据，不能仅写一个总分；质量阻断按第 6.3 节处理。
7. **结果提交**：API 独立验证所有结果与准确数量。全部可交付才提交整批；部分失败保留成功检查点和受控预览，明确剩余条数。只恢复失败范围；若视频已全部合格而最终提交短暂失败，仅恢复验证/提交，不重新规划、渲染或合成。

每个阶段有预算、最大尝试次数、退避和取消检查；不无限自动重写/重渲染。供应商创建结果未知时停止自动创建并记录可核查状态；已有 providerTaskId 只继续轮询/下载。不能承诺进程崩溃窗口下供应商严格一次计费，恢复协议必须验证重复收费风险并提供人工处理入口。

并发、创建 QPS、下载/编码额度与账号总配额明确配置；本期先单消费者实例运行，不能照搬其他 Worker 的 20 路并发。多实例前补账号级总限流。LangGraph 仅用于确需检查点/重试/分支的业务图，简单调用不用额外框架；大文件与模型正文不进入消息或 Graph State。

### 6.3 执行恢复与质量返修

批次协调任务负责聚合条目执行结果与发布；条目完成不等于批次已提交。首次批次有失败/告警条目时保留 PARTIAL 或失败投影，不降低 requestedCount。所有子任务已停止执行后，协调任务可以以失败终态保留恢复信息；显式条目重试或返修在一个事务内恢复协调状态并安排必要聚合步骤，不要求浏览器再次点击整批完成。批次取消会阻断子任务发布；迟到结果只按取消/租约规则处理，不能恢复已取消批次。

| 场景                           | 恢复入口与范围                                                  | 检查点规则                                                                                                                  |
| ------------------------------ | --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| 全批规划失败、尚未派发条目     | 协调 task retry，只恢复公共规划                                 | 固定 batch/variant ID 和来源快照；规划成功并持久化后才创建条目 Outbox；并发条目请求不能重复触发规划                         |
| 网络、下载、编码或审片调用失败 | 条目 retry，恢复对应失败步骤                                    | 重用同输入下有效结果和 providerTaskId；编码失败不重渲染，审片调用失败不重合成                                               |
| 已有媒体但质量 WARNING/FAILED  | 条目 repair，按该次失败执行任务的冻结来源快照补证或修复指定缺陷 | 新建内部 repairAttemptId，记录修复依据和采用的计划哈希；仅使受影响步骤及其下游失效，无关镜头/条目继续复用；旧尝试回写被拒绝 |
| 全部条目合格、最终提交暂时失败 | 协调 task retry，只恢复验证/原子提交                            | 不调用模型或 FFmpeg；重验来源/目标版本，冲突明确失败，重复成功完成返回原收据                                                |
| 已提交条目主动采用最新配置     | 条目 regenerate                                                 | 使用最新确认来源，成功原位提交目标 video/batch；失败保留旧交付；首次未提交批次不开放此入口                                  |

WARNING 表示证据不足，不能作为通过或无限重审同一结果。若可通过额外证据解决，仅补抽帧/检测/审片，保留原始报告和新增证据；证据充分后转 PASSED，证实缺陷则转 FAILED，仍不能判断则保留 WARNING 并结束当前尝试。FAILED 按缺陷定位执行返修：画面问题重做指定镜头及合成/质检，字幕或音轨问题只重做对应轨道及合成/质检。不能修复或预算耗尽时任务以安全原因结束，展示未交付条目及可操作原因，不自动降级通过。产品事实、用户映射和结构锁定不能被返修改写；需改变这些内容时走上游编辑与新来源流程。

repair 请求须明确关联失败执行任务及候选，不从当前批次头猜来源：首次生成沿用该批次冻结快照；已提交条目按新来源 B 重生成后失败，返修继续该次 regenerate 的 B 快照、目标版本与检查点，不能退回首次批次 A。该来源再变化时，按来源失效规则阻断，不拼接另一任务的候选。

返修只生成内部候选，不提前增长 WorkingArtifact revision；合格后按首次整批或局部更新提交边界采用。补证、规划修正和重渲染均计入所关联执行任务持久化的预算与尝试上限，重领或 retry 不重置额度。初次生成授权范围内的自动修正须有明确上限；达到上限后停止，用户明确选择有预算的修复操作才能继续。供应商创建结果未知不属于质量返修，必须先核查，不能通过 repair 绕过重复收费保护。

### 9.2 真实生成与质量验收

使用有权测试、非敏感的参考片和目标商品资料。测试集至少覆盖有/无口播、快切与长镜头、烧录字幕、商品多角度，以及不支持音轨保留时的明确阻断。记录输入和确认版本、配置、供应商请求/任务ID、调用次数/费用、耗时、成片与报告；不记录密钥、签名地址或敏感完整Prompt。

| 验收目标       | 本计划测量口径                                                                                                                                                                              |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 数量           | 一条参考视频，同批实际生成 10 条完整成片。逐条核验可播放、可下载且通过质量检查                                                                                                              |
| 差异化         | 每条有可追溯 VariantPlan，在映射允许的场景/人物/事实侧重/叙事细节中存在实际可见差异；自动证据与人工对照一致，不能仅改种子/标题，也不能改变 KEEP、精确替换目标或锁定结构                     |
| 结构与节奏     | 镜头顺序与阶段作用保持；按第 4.1 节冻结的帧时间线对比实际剪辑边界，总时长与镜头边界偏差≤1输出帧，音频锚点偏差≤100ms；含转场重叠且不累积漂移。此为合成门槛，生成动作本身是否卡点另由审片验证 |
| 产品事实与映射 | 全部必换产品在适用镜头正确出现，无原商品名称/包装/未经依据功效残留；不支持的保留/替换策略任务前阻断                                                                                         |
| 画面与音频     | 无明显换物违和、主体漂移、穿模、闪烁、接缝及重复音轨；字幕与口播不冲突，既定静音/节拍区间保留；无法确认项保留质量预警，不自动通过                                                           |
| 评审证据       | 每条保留自动检测、AI审片逐镜依据及人工验收记录；两名评审按同一清单判定，通过条目须均为可交付，有分歧则记缺陷并重验，不用无定义的“匹配分数”替代                                              |

上述时间/质量门槛是待验证的验收目标；G0/G3 应先证实技术可行性。达到接口闭环不等于通过画面质量验收；不能把未授权、跳过、告警或缺供应商配置记为通过。不引入“结构匹配率80%”之类未定义算法作为完成依据。
